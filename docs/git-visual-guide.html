01The model

Trunk-based, with release branches cut from main. No permanent develop branch — its only job is holding merged-but-unreleased work, and a release branch does that better because it exists only during the stabilization window instead of forever.

The three rules

1. Everything merges to main; main is always green.  2. A release branch is cut when the train departs, not when work starts — only stabilization commits land on it.  3. Fixes made on a release branch merge back to main, or you ship the same bug again next release.

Term

Tag — an immutable name for one exact commit. A branch pointer moves as you commit; a tag never does, which is why releases are tagged rather than branched.

02Conventions

Four names get written by hand on every ticket: the branch, the PR title, the commit subjects on the branch, and the body text. Only one of them is load-bearing — and it is not the one most people are careful about. This section says which, and why.

Branch names

Git has no idea what "client" or "server" means — a branch always spans the whole repo. The prefix is convention, and nothing but discipline stops you editing server/ on a client/ branch.

BranchUse
mainTrunk. Protected. Never commit directly.
client/mp-02-route-treeFrontend ticket
server/mp-12-auth-endpointsBackend ticket
mp-31-fetch-hookTouches both — no prefix
docs/conventions-sectionDocs only
chore/git-01-ci-and-releasesTooling, CI, config
release/1.4Stabilization for the 1.4 train
hotfix/1.4.1-token-refreshUrgent fix against a shipped release

Lowercase, hyphen-separated, ticket id first after the prefix. The branch is where the ticket id lives — it no longer appears in the commit subject, so this is the link back to ROADMAP.md that survives the whole flow.

The reliable filter is paths, not names — this one git actually enforces:

git log --oneline -- client/        # every commit touching the client
git diff main --stat -- server/

The PR title — the only one that matters

Merges are squash merges. Every commit on your branch collapses into a single commit on main, and that commit's message is the PR title. release-please then reads nothing but the commit subjects on main to compute the next version number.

Why it is irreversible

Rewriting a message on main means rewriting pushed history. The title you type in the PR box is the one you keep — which is why .github/workflows/pr-title.yml fails the PR before it can become history.

<type>(<scope>): <subject>

feat(client): show the app version in the header
fix(server): send sameSite on the refresh cookie
ci: run vercel commands from the repo root
PartRuleEnforced
typeOne of feat fix perf refactor docs test chore ci build revertyes
scopeclient or server. Optional — omit it when the change spans both.yes
subjectStarts lowercase, imperative mood, no trailing period, ~72 chars.yes
ticket idNot here. It belongs in the branch name and the PR description.—

✗ rejected

shopping list stuff
feat(cleint): add filters
Feat(client): add filters
feat(client): Add filters.
feat(client): MP-72 add filters

No type; misspelled scope; capitalised type; capital subject plus a full stop; ticket id in the subject.

✓ accepted

feat(client): add ingredient filters
fix(client): keep row values on delete
docs: add a conventions section
chore(client): bump antd to v6.7
feat(client)!: return Paginated<Recipe>

The last one is a breaking change — the ! forces a major bump.

GitHub appends (#12) to the squashed subject automatically. That is expected and release-please parses straight through it.

Version bumps, by type

TypeMeaningBump
featNew user-visible capabilityminor — 0.2.0 → 0.3.0
fixBug fixpatch — 0.2.0 → 0.2.1
perfFaster, same behaviourpatch
refactor docs test chore ci buildNo behaviour change for usersnone
feat! or BREAKING CHANGE: footerIncompatible changemajor — 0.2.0 → 1.0.0

The bump comes from the set of commits since the last release, not from each one: three feats still produce a single minor bump. Highest wins — any breaking change makes it major, else any feat makes it minor, else patch.

Commit subjects on your branch

These get squashed away, so they never reach main and never affect a version number. wip and fix typo genuinely do no harm.

Write them conventionally anyway. Not for the tooling — for the moment you open the PR and need a title, when a branch of well-formed subjects hands you one already written. And because the habit has to be automatic before the day you cut a release branch, where merges are --no-ff and every subject does reach the history release-please reads.

The body

Optional, and worth writing whenever the subject line leaves a "but why" hanging. Blank line after the subject, wrapped at ~72 columns, present tense.

fix(client): keep ingredient rows stable on delete

Rows were keyed by array index, so removing the middle row made React
reuse the wrong DOM nodes and the remaining two lost their values.
Key by the row's generated id instead.

Refs: MP-42

Say why, not what. The diff already shows what changed; it cannot show what you tried first, which constraint forced the approach, or which bug report sent you here. That is the part future-you cannot reconstruct.

Two footers carry meaning:

  • Refs: MP-42 — the ticket link, now that the subject has no room for it. Put it in the PR description too; a squash merge copies the description into the commit body.
  • BREAKING CHANGE: mealsApi.list now returns Paginated<Recipe> — forces a major bump and lands verbatim in CHANGELOG.md. Works from the PR description on a squash merge, exactly like ! in the subject.

Release PR titles are generated — and still checked

release-please writes its own PR titles from pull-request-title-pattern in release-please-config.json. Those PRs face the same title check as yours, so the pattern has to produce something the check accepts — a valid type, and any scope drawn from the allowed list.

release-please's default pattern renders the component as a scope with a stray space, chore( client): release 0.2.0, which the check rejects as an unknown scope. Hence the explicit pull-request-title-pattern in the config. Change one of those two files and re-check the other.

The one rule

Be as sloppy as you like on your branch. Be exact in the PR title box — it is the only text in the whole flow that becomes permanent, drives the version number, and cannot be edited afterwards.

03Why fixes must merge back

A commit exists only on the branch you made it on. Git propagates nothing on its own. Here is what that costs when you forget.

git switch main && git pull
git merge --no-ff release/1.4
git push

This is the single most common release-flow mistake. Put it in the release checklist.

04Hotfixes

Production is on v1.4.0 and a user hits an infinite login-refresh loop. Meanwhile main has moved on — half-finished filter work, a partly-migrated API layer. None of it is shippable, so you can't fix on main and deploy.

Branch from the tag instead. That is the exact code running in production.

git switch -c hotfix/1.4.1-token-refresh v1.4.0   # branch FROM THE TAG
git commit -m "fix(client): stop refresh loop on expired token"
git tag -a v1.4.1 -m "Hotfix 1.4.1"
git push origin hotfix/1.4.1-token-refresh v1.4.1

git switch main && git merge --no-ff hotfix/1.4.1-token-refresh

Also merge the hotfix into any live release branch — release/1.5 was cut before the fix existed, so it needs it too.

05Merge vs cherry-pick

Term

SHA — a commit's id, a fingerprint hashed from its files, message, author and parent. Change any byte and you get a different SHA, which is why the same fix on two branches is two unrelated commits.

Term

Cherry-pick — copy one commit's changes onto another branch, ignoring its history. You get a new commit with the same diff and a different SHA.

The clean rule is directional:

DirectionUseWhy
release/1.4 → mainmergeYou want everything on that branch
main → release/1.4cherry-pickYou want one fix, definitely not main's new features
The catch

Cherry-pick applies text; it does not check the result makes sense. If P's fix uses a helper that D introduced, the patch applies cleanly onto a branch without D and then fails at runtime. Git reports textual conflicts, never semantic ones — always build and test on the target branch.

Use git cherry-pick -x to stamp "cherry picked from commit a1b2c3d" into the message. Costs nothing, and in six months it explains where the duplicate came from.

06Worked example

A fix made on a half-finished feature branch, needed in 1.4 before the feature is ready. X is the fix; X′ is its cherry-picked copy on main; H is the eventual merge of the feature branch.

*   6606c31 (main, tag: v1.5.0, release/1.5) H: merge client/mp-42-recipe-form
|\
| * cf178fe (client/mp-42-recipe-form) Z: prep items
| * f60bc9d Y: ingredient rows
| * ea8efa3 X: fix(client) dayjs week start      ← original
| * 152eecb W: recipe form scaffold
* | ae63bf0 G
| | * 763d0fe (tag: v1.4.0, release/1.4) stabilize 1.4
| |/
|/|
* | 47feda3 F
* | 4a88cfb X': fix(client) dayjs week start     ← cherry-picked copy
|/
* 3e9ece9 E

✓ What worked

v1.4.0 shipped with the fix and without the unfinished form. v1.5.0 got both. The merge at H was clean — both sides had made a byte-identical change, so git's three-way merge took it once.

✕ What it cost

The fix appears twice in v1.5.0's history under two SHAs, permanently. Had the cherry-pick been adapted during a conflict, H would have conflicted — over a fix already made.

One ordering detail that's easy to get wrong: X′ sits before F, and release/1.4 is cut from F. That is the only reason v1.4.0 contains the fix. Cherry-pick after cutting the branch and you'd have to cherry-pick onto release/1.4 separately.

07Environments are not releases

An environment is a place. A version is what's deployed there. Three environments does not mean three release lines — it means one artifact being promoted.

EnvRunningTrigger
devlatest mainevery push (automatic)
qav1.5.0-rc.2any v*-rc.* tag
prodv1.4.0final v* tag + manual approval

That looks like three live versions but isn't — prod will move to 1.5.0 and 1.4.0 disappears. Genuine multi-release support means patching 1.4 and 1.5 indefinitely because different customers are stuck on each. Here nobody is stuck; you just haven't promoted yet.

08Rollouts

Term

Rollout — how a new version reaches users: all at once, or gradually. The gradual kinds exist so a bad release hits a small fraction of traffic before you notice and stop it.

StrategyHowRollback
Big bangReplace everything at onceRedeploy the old version — slow
RollingUpdate servers one at a timeRoll the rest back mid-flight
Blue-greenTwo identical stacks; flip the routerFlip back — seconds
Canary5% → 25% → 100%, watching metricsRoute the slice back

Feature flags are the related-but-different one: code ships to 100% of servers with the feature off, then you enable it for 5% of users. Same gradual exposure, no deployment in the ramp — and you can kill it without a rollback.

09Changelogs

A changelog is the human-readable "what changed in this version." Its audience is whoever is deciding whether to upgrade — including you in six months. With conventional commits you write none of it: the changelog is a projection of messages you were writing anyway.

Commits you wrote

feat(client): aggregate the weekly
  shopping list

fix(client): stop macros showing
  NaN when servings is 0

chore(client): bump vite to 8.3.1

CHANGELOG.md generated

## 0.5.0 (2026-10-01)

### Features
* client: MP-72 weekly shopping

### Bug Fixes
* client: MP-62 macros show
  NaN when servings is 0 (f9e8d7a)

10One-time deployment setup

Four services, wired once and then left alone. GitHub holds the code and runs the pipeline; each host watches the repo and takes only the folder it owns.

The five config files

FileWhat it doesWhen it runs
.github/workflows/ci.ymlLint, typecheck, build. Path-filtered so a docs edit doesn't build the client.every PR + push to main
.github/workflows/release-please.ymlReads conventional commits, maintains the Release PR, creates the tag when it's merged.push to main
release-please-config.jsonDeclares client and server as separately-versioned packages.read by the above
.release-please-manifest.jsonCurrent version of each package. release-please rewrites it.read + written

Term

Deploy hook — a secret URL a host gives you; POST to it and that service redeploys. It's how a GitHub Action triggers Render without Render needing to watch the repo itself.

A · Vercel — frontend

  1. New Project → import malvibhatt/meal-planner.
  2. Root Directory: client. Framework preset Vite; build npm run build; output dist.
  3. Env var VITE_API_URL → your Render URL.
  4. Settings → Git → set Production Branch to something unused (e.g. production) so pushes to main make preview deploys only. Production then happens only from the tag workflow.
  5. Grab VERCEL_TOKEN, VERCEL_ORG_ID, VERCEL_PROJECT_ID → GitHub repo Settings → Secrets.

Preview deploys per PR come free and are the single best reason to use Vercel here — every PR gets a real URL to click before you merge.

B · Render — backend

  1. New → Web Service → same repo. Root Directory: server.
  2. Build: npm ci && npx prisma generate && npm run build. Start: npm start.
  3. Pre-Deploy Command: npx prisma migrate deploy — runs migrations before the new code goes live.
  4. Env: DATABASE_URL, JWT_SECRET, CLIENT_ORIGIN, NODE_ENV=production.
  5. Turn Auto-Deploy off. Settings → Deploy Hook → copy the URL into a GitHub secret RENDER_DEPLOY_HOOK.

C · Supabase — database

  1. New project, pick a region near your Render region.
  2. Connection string → use the pooler URL (port 6543) for the app, direct (5432) for migrations.
  3. Put the pooler URL in Render's DATABASE_URL; add DIRECT_URL for Prisma's directUrl.
  4. Keep a separate free project for local/dev, or run Postgres in Docker locally — never point dev at prod.
Do you need Docker and Kubernetes?

No — and adding them would cost you the React time you're trying to protect. Vercel and Render already containerize your app for you; Render builds an image from your repo without you writing a Dockerfile. Kubernetes solves orchestrating many services across many machines with a team operating it — you have two services and one developer. The one place Docker genuinely earns its keep here is local Postgres via docker-compose, so your machine matches Supabase. Revisit containers if you ever need system-level dependencies Render can't install; revisit K8s essentially never on a project this size.

11A feature, end to end

Shipping MP-72, the weekly shopping list — a feature that touches the database, the API and the UI, so it exercises every part of the pipeline.

Correction worth reading first

Merging your feature PR into main does not create a tag. release-please instead opens (or updates) a Release PR titled "chore: release client 0.5.0". The tag is created when you merge that second PR. This two-step is deliberate: automation proposes the version, you decide when to ship. Several features can accumulate in one Release PR before you release them together.

  1. Branch from main you

    git switch main && git pull
git switch -c server/mp-72-shopping-list

    Server first — the client can't be built against an endpoint that doesn't exist.

  2. Commit, conventionally you

    npx prisma migrate dev --name add_shopping_list_view
git add -A
git commit -m "feat(server): add the weekly shopping list endpoint"
git push -u origin server/mp-72-shopping-list

    The feat(server): prefix is what later becomes a minor version bump and a changelog line. A wrong prefix here means a wrong version number.

  3. CI runs on the PR automatic

    ci.yml sees server/** changed, runs only the server job: npm ci, lint, tsc --noEmit, tests. The PR shows a red or green check. Vercel posts a preview URL if the client changed.

  4. Read your own diff, then squash-merge you

    The PR title becomes the commit message on a squash merge — so the title must be conventional format, not "shopping list stuff". Repeat steps 1–4 for client/mp-72-shopping-list-page.

  5. release-please opens the Release PR automatic

    It scans commits since the last tag, finds two feat: entries, and opens "chore: release client 0.5.0 / server 0.2.0" containing the bumped package.json, the updated manifest, and a written CHANGELOG.md. Nothing has shipped yet.

  6. Merge the Release PR when you're ready to ship you

    This is the release decision. Leave it open to batch more features in; merge it to cut the release.

  7. Tags and GitHub Releases appear automatic

    client-v0.5.0
server-v0.2.0

    Plus a GitHub Release per tag, with the changelog section as its notes.

  8. deploy.yml ships it automatic

    on:
  push:
    tags: ['client-v*', 'server-v*']

    Order matters: server first (Render's pre-deploy runs prisma migrate deploy), then client. Ship a client that calls an endpoint that isn't live yet and you've broken production for the minute in between.

  9. Verify 2 min

    curl https://meal-planner-api.onrender.com/health
git describe --tags        # client-v0.5.0

    Then open the shopping list page in prod. If it's wrong, go to §12.

12Hotfix & rollback in production

Scenario A — hotfix, step by step

client-v0.5.0 is live. The shopping list crashes on an empty week. main already has half of Phase 6 merged, so you cannot ship from main — it would carry unfinished work into production.

Term

ref — a name pointing at a commit. Branches live under refs/heads/, tags under refs/tags/. A tag is not "on" a branch; it points straight at a commit, which is why pushing one is its own action.

  1. Find out what production actually runs you

    git fetch --tags
git tag -l 'client-v*' --sort=-v:refname | head -3

    Don't assume. Cross-check against the GitHub Releases page or the live Vercel deployment before you branch.

  2. Branch from the tag, not from main you

    git switch -c hotfix/0.5.1-empty-week client-v0.5.0

    You now have production's exact code. Anything you add is the only difference between what's live and what you'll ship.

  3. Reproduce, fix, commit you

    git commit -m "fix(client): guard an empty week in the shopping list"

    fix: not feat: — it's a patch bump. Keep it to the single smallest change that stops the crash; a hotfix is not the moment to tidy anything.

  4. Push the branch you

    git push -u origin hotfix/0.5.1-empty-week

    Pushes the commit, not a release. Nothing deploys yet.

  5. CI validates the branch automatic

    ci.yml runs lint, typecheck and build. Wait for green. A hotfix that fails to build turns one incident into two.

  6. Open a PR into main — but don't wait for it you

    This exists so the fix reaches main (§03). You are not blocked on merging it; shipping happens via the tag in the next step, in parallel.

  7. Create the tag and push it to origin you

    git tag -a client-v0.5.1 -m "Hotfix 0.5.1 — empty week crash"
git push origin client-v0.5.1

    Where does it go? To origin — the same remote your branches go to. A tag isn't pushed onto a branch; it becomes refs/tags/client-v0.5.1 on GitHub, pointing at the commit you just made. Plain git push would not have sent it — tags always need naming explicitly.

  8. deploy.yml fires on the tag automatic

    The workflow checks out the tagged commit — not main, not the branch tip — builds it, and deploys. That's why production gets exactly the code you tested and nothing else.

  9. Verify in production 2 min

    Load the page that was crashing. If it's still broken, roll back (Scenario B) rather than attempting a second hotfix under pressure.

  10. Merge the PR so main has the fix you

    Skip this and 0.6.0 reships the crash. This is rule 3 from §01, and it is the step people forget once the pressure is off.

  11. Tell release-please the version already went out you

    // .release-please-manifest.json
{ "client": "0.5.1", "server": "0.2.0" }

    Include this edit in the merge-back PR. In manifest mode release-please tracks versions in that file, not from your tags — so without it, it will happily propose 0.5.1 a second time and collide with the tag you just pushed.

Why the hotfix is tagged by hand

release-please only watches main, and main is exactly what you can't ship during an incident. So a hotfix is the one release you tag manually — which is also why step 11 exists, to put the automation back in sync afterwards.

Scenario B — rollback

Code rolls back in seconds. Data does not. That asymmetry is the whole problem.

LayerHow to roll backTime
Vercel (client)Dashboard → previous deployment → Promote to Productionseconds
Render (server)Dashboard → Events → previous deploy → Rollback~1 min
Supabase (schema)No safe automatic undo. See below.—

If v0.5.0 dropped a column and you roll the server back to v0.4.0, the old code queries a column that no longer exists. The deploy rolled back; the database didn't.

The rule

Every migration must leave the previous release still working. Add columns nullable; rename by adding-then-copying rather than RENAME; drop only after a release has passed. Follow this and rollback is always "click the previous deploy." Break it and rollback means restoring a database backup.

13Scheduled & partial releases

When the Release PR actually opens

release-please.yml runs on every push to main. Each run it looks at commits since the last release and either opens the Release PR, updates the one already open, or does nothing.

Commits since last releaseResult
only chore: docs: test:nothing — no PR
the first feat: or fix:opens the Release PR
anything releasable after thatupdates the same PR — new version, new changelog

One long-lived PR that keeps rewriting itself until you merge it. And the version comes from the set of commits, not each one: three feat:s since 0.4.0 still produce 0.5.0, a single minor bump. Highest bump wins — any breaking change makes it major, else any feat: makes it minor, else patch.

The sprint release

That accumulating PR is a scheduled-release mechanism. Nothing ships until you merge it, so merging it on the 30th is what cuts the release.

Config change for coordinated releases

Set "separate-pull-requests": false in release-please-config.json. You get one Release PR bumping both client and server, so merging once tags both. With true you'd have two PRs to merge in the right order every sprint — friction you don't want when the halves ship together anyway.

Feature flags — deploy is not release

The cleanest answer to "this is merged but shouldn't ship" is to make shipping it harmless. A flag separates code reaching the server from users seeing the feature.

Worked example. MP-82 "suggest more like this" is merged, but the ranking is still bad. Rather than keeping it off main:

// client/src/config/flags.ts
export const flags = {
  mealSuggestions: import.meta.env.VITE_FF_SUGGESTIONS === 'true',
};

// client/src/pages/Dashboard/DashboardPage.tsx
{flags.mealSuggestions && <SuggestionsPanel />}

Set VITE_FF_SUGGESTIONS=false in Vercel's production env and true in preview. Now main ships whenever you like; you and your preview URLs see the panel, production doesn't.

Build-time vs runtime flags

Vite inlines import.meta.env.VITE_* at build time, so flipping the value needs a rebuild and redeploy — fine for "not this sprint", useless as a kill switch. For instant toggles, serve flags from the API (GET /config/flags) and read them at runtime. The server side is different: Node reads process.env at runtime, so a backend flag flips with a restart.

Flags are debt. Delete each one once its feature is permanent, or you accumulate dead branches nobody dares remove.

Partial release — shipping A but not B

v2.0.0 is live. Since then A and B merged to main and C is in progress. You now decide to ship A only. Cut a release branch from the commit where A landed — the point before B.

  1. Find where A landed you

    git log --oneline main

  2. Cut the branch from that commit you

    git switch -c release/2.1 <sha-of-A-merge>
git push -u origin release/2.1

  3. Point release-please at the branch you

    on:
  push:
    branches: [main, 'release/**']
# in the step:
with:
  target-branch: ${{ github.ref_name }}

  4. A Release PR opens on that branch automatic

    It sees only A and proposes 2.1.0.

  5. Merge it — tag and deploy follow you

    deploy.yml fires on v2.1.0. Production has A and not B.

  6. Merge the release branch back into main you

    git switch main && git pull
git merge --no-ff release/2.1
git push

    release-please wrote the manifest bump and changelog onto the release branch. If that never reaches main, main still reads 2.0.0 and its next release proposes 2.1.0 a second time — colliding with the tag you already pushed.

Where the version number actually lives

.release-please-manifest.json is an ordinary tracked file. Nothing magic: it changes only when a commit changes it, and merges carry it like any other file. Only release-please edits it, and only in the commit created when you merge a Release PR.

That single fact explains the whole sequence below — including why main can sit at 2.0.0 while v2.1.0 already exists on GitHub.

  1. A and B merge to main you

    // .release-please-manifest.json on main
{ "client": "2.0.0" }        // unchanged

    A Release PR is open proposing 2.1.0 with both A and B in its changelog. Its edits live on release-please's own branch (release-please--branches--main), not on main. You never merged it, so main's file still reads 2.0.0.

  2. Cut release/2.1 from A's commit, merge its Release PR you

    // on release/2.1 — commit R, written by release-please
{ "client": "2.1.0" }        // changed HERE

// on main — untouched
{ "client": "2.0.0" }

    The file became 2.1.0 on the release branch, because that is where you merged a Release PR. Tag v2.1.0 points at commit R, and deploy.yml ships it.

  3. Merge release/2.1 back into main you

    git switch main && git pull
git merge --no-ff release/2.1
git push

// .release-please-manifest.json on main
{ "client": "2.1.0" }        // now, because of the merge

    An ordinary merge commit carrying R's file changes — the manifest bump and the 2.1.0 changelog section.

  4. release-please recomputes on main automatic

    Last release now reads 2.1.0; the only unreleased commit is B. It updates the existing PR — retitling it from "release 2.1.0" to "release 2.2.0" and rewriting the changelog to hold only B. You will not get a second PR to reconcile.

After this eventmanifest on mainRelease PR on main then proposes
A merged2.0.02.1.0
B merged2.0.02.1.0 — still; one minor bump covers both
release/2.1 tagged v2.1.02.0.02.1.0 — main doesn't know yet
release/2.1 merged back2.1.02.2.0 — only B is unreleased
Row three is the dangerous state

v2.1.0 exists on GitHub, but main still believes the last release was 2.0.0. Merge the Release PR on main while in that state and release-please tries to create v2.1.0 again — colliding with the tag already pushed. The merge-back is what closes the window, so do it immediately after tagging, not "later".

Why no changelog conflict: main's CHANGELOG.md and manifest are untouched while a Release PR sits open, since those edits live on release-please's branch. So the merge brings the 2.1.0 section cleanly, and 2.2.0 is later added on top — leaving a history that reads the way it actually happened: A shipped first, B second.

Row three works, but don't let it become routine — every release branch is a merge-back you have to remember, and the manifest desync is silent until it bites.

14Three environments: two models

One release-please, never one per environment

release-please produces versions and tags; environments consume them. There is one version line — v2.1.0 is v2.1.0 whether it sits in QA or prod. A Release PR per environment would mean dev had its own version number, defeating the point of promoting one artifact. The rule: one Release PR per branch release-please targets, never per environment.

Deployment, release and exposure are three different events. They only look like one because on production they happen together.

Model A — freeze main

One line, no release branch. Between code-freeze and release day, nothing merges to main except fixes. QA deploys main on demand.

That third QA run is the final sign-off on the commit about to be tagged — skip it and f2 reaches production having never been tested. One honest detail: prod isn't byte-identical to what QA approved, because merging the Release PR adds a commit. But it touches only CHANGELOG.md, package.json and the manifest — no source — so the built app is the same.

Model A — the workflows

# deploy-dev.yml
on:
  push:
    branches: [main]          # every merge → dev

# deploy-qa.yml
on:
  workflow_dispatch:          # ← puts a "Run workflow" button in the Actions tab
    inputs:
      ref:
        description: 'Branch or tag to deploy'
        default: 'main'

# deploy-prod.yml
on:
  push:
    tags: ['v*']              # only a tag reaches production

workflow_dispatch is the whole mechanism behind "the QA team ran a pipeline" — a button in the GitHub Actions UI, with a ref input so they can also pick a specific tag.

The freeze is a rule, not a git feature

Nothing in git enforces it. Teams use, weakest to strongest: 1. a Slack announcement; 2. branch protection — temporarily require an extra approver on main, or restrict merge rights to the release manager; 3. a CI check that fails any PR without a hotfix label while a freeze flag is set. Most teams do 1 and rely on discipline.

The branch is the freeze, so main never closes. QA tracks the release branch automatically.

Model B — the workflows

# deploy.yml — one file, three routes
on:
  push:
    branches:
      - main               # → dev
      - 'release/**'       # → QA
    tags:
      - 'v*'               # → prod

# release-please.yml — targets both branches
on:
  push:
    branches: [main, 'release/**']
with:
  target-branch: ${{ github.ref_name }}

Targeting both branches means two Release PRs during the window: the one on main is a preview of the next release — ignore it — and the one on release/2.1 is the one you merge. After the merge-back, main's recomputes to 2.2.0 with D and E (§13).

Which to pick

Model A — freeze mainModel B — release branch
Complexityone line, nothing to merge backbranch + merge-back + manifest sync
Team during freezeblocked — nobody mergesunaffected — main stays open
QA deploysmanually, from mainautomatically, from the branch
Accidental feature in the releasepossible — anything merged shipsimpossible — it isn't on the branch
Manifest desync risknonereal (§13)

Model A trades a few days of merge throughput for a much simpler git model — often the right call for a small team. Model B only pays off once idling people costs more than the branch bookkeeping.

For meal-planner

Model A, and skip QA entirely. A QA environment with no QA team is a service to maintain for nothing — use Vercel's per-PR preview deploys instead, which give you a real URL per branch for free. So: dev tracks main, prod deploys on tag, "freeze" means "don't merge for a bit". Add Model B when a second person needs to test something you haven't merged.

15Glossary

TermTwo lines
SHAA commit's id — a fingerprint hashed from its files, message, author and parent. Change any byte and the SHA changes, so the same fix on two branches is two unrelated commits.
tagAn immutable name for one exact commit. Branch pointers move as you commit; tags never do — which is why you tag releases. Use -a for anything you ship.
cherry-pickCopy one commit's changes onto another branch, ignoring its history. Produces a new commit: same diff, different SHA.
merge --no-ffJoin two histories, forcing a merge commit even when a fast-forward is possible. Keeps each ticket a visible unit in git log --graph.
backportApply a fix made on main to an older release branch, usually by cherry-pick. Lets you patch a frozen version without dragging in new features.
rolloutHow a version reaches users — all at once, or gradually. Gradual kinds limit how many people a bad release can reach before you stop it.
canaryA rollout that sends a small traffic slice to the new version first, watching error rates before ramping up. Abort by routing the slice back.
blue-greenTwo identical production stacks; deploy to the idle one and flip the router. Rollback is flipping back, so it takes seconds.
Release PRThe pull request release-please keeps open on a branch, holding the pending version bump and changelog. Merging it is what creates the tag.
manifest.release-please-manifest.json — the file recording each package's current version. release-please reads versions from here, not from your tags.
feature flagA switch that keeps shipped code turned off until you enable it. Decouples deploying from releasing, and kills a feature without a rollback.
workflow_dispatchA GitHub Actions trigger that adds a "Run workflow" button instead of firing on a push. How a QA team deploys on demand rather than automatically.
code freezeAn agreed window where nothing merges to the release line except fixes. Enforced socially or by branch protection — git itself has no such concept.
rcRelease candidate — a pre-release tag like v1.5.0-rc.2 marking a build under test. Promoted unchanged to v1.5.0 if it passes.
LTSLong-term support: a version you've promised to patch for a fixed window. Angular keeps ~3 majors alive at once, which is why backporting exists.

16Cheat sheet

# daily
git switch main && git pull
git switch -c client/mp-02-route-tree
git commit -m "feat(client): add the route tree"
git push -u origin client/mp-02-route-tree

# inspect
git log --graph --oneline --decorate --all   # topology
git log --oneline -- client/                 # commits touching client
git describe --tags                          # how far past the last tag
git show <sha>                               # what one commit changed

# tags
git tag -a v1.4.0 -m "Release 1.4.0"
git push origin v1.4.0        # tags are NOT pushed by plain `git push`
git push --tags               # push all tags

# moving changes
git merge --no-ff release/1.4          # bring a whole branch
git cherry-pick -x <sha>               # bring one commit's diff

# undo
git switch --detach v1.4.0    # inspect exact released code
git revert <sha>              # safe on shared branches
git reset --hard <sha>        # ONLY on unpushed local work
Five things worth memorising

1. Annotated tags (-a) for anything you ship. 2. git push ignores tags — push them explicitly. 3. Never rewrite pushed history; use revert. 4. Merge release-branch fixes back to main. 5. A branch pointer moves; a tag never does.
