Release Pipeline Playbook

Everything it takes to get a new project from git init to a production URL that only changes when you decide it should. Every step carries three things: what to do, why it works that way, and what breaks — because in this setup almost every failure is silent.

Part A

The git loop you repeat

Learn this first — every other part of the playbook is delivered through it. One ticket, one branch, one PR, one squash commit.

01

Start from a fresh main

your terminal, before any work

Do 
git switch main
git pull --prune
Why

Branching from a stale main gives you a merge conflict later for no reason. --prune is the half people skip: it deletes the local origin/xxx pointers whose branches are already gone from GitHub. Those pointers are just a cached copy of the remote, and they linger forever otherwise.

Watch out

git status saying "up to date with origin/main" proves nothing before a fetch — it is comparing against that same stale cache. Pull first, then believe it.

02

Cut the branch locally, then publish it

never create the branch in the GitHub UI first

Do 
git switch -c client/mp-02-route-tree   # creates it locally + switches
git push -u origin client/mp-02-route-tree

Naming: client/… or server/… for one half, no prefix when it spans both, docs/… for docs, ci/… for pipeline work.

Why

The branch is local until you push; -u creates it on the remote and records the upstream, so plain git push and git pull know where to go from then on. The branch name is also where the ticket id lives, since it is no longer allowed in the commit subject.

Watch out

Uncommitted changes follow you across branches. git switch -c does not leave them behind, so anything dirty in your tree lands in the wrong PR. Run git status before cutting, and commit or stash first.

03

Commit in conventional format

this format is the input to your version numbers

Do 
git commit -m "feat(client): add route tree with nested layouts"
git commit -m "fix(server): set sameSite on the refresh cookie"

Subject starts lowercase, imperative mood, no trailing period, under ~72 chars. No ticket id.

Why

feat bumps the minor version, fix and perf bump the patch, and chore/docs/ci/test release nothing. A tool reads these strings literally and decides your version number from them. A sloppy message is a wrong version.

Watch out

Check the author before you push: git log -1 --format="%an <%ae>". A commit made under the wrong email is trivially fixed while unpushed (git commit --amend --reset-author --no-edit) and permanent afterwards.

04

Open the PR and read your own diff

github.com — the PR title is the part that matters

Do
  • Title the PR in the same conventional format as the commit — this becomes the squash commit message.
  • Read the Files changed tab before merging.
  • Locally, the same diff is git diff main...HEAD.
Why

Three dots compares against the point where your branch split off, so main moving ahead never pollutes the view. Two dots compares the two tips and shows main's new commits inverted, as though you deleted them. Three dots is what GitHub shows.

Reviewing your own diff costs thirty seconds and catches stray console.logs, a leftover any, and files you never meant to commit.

Watch out

git log is the opposite convention: git log main..HEAD with two dots lists the commits on your branch. Easy to mix up.

05

Squash merge, then clean up in three places

the cleanup people get wrong

Do
  • Click Squash and merge, then Delete branch on the PR page.
git switch main
git pull --prune                       # fast-forwards + drops the stale origin/ ref
git branch -D client/mp-02-route-tree  # capital D, see below
Why

A branch exists in three places: locally, as a cached origin/… pointer on your machine, and on GitHub. Deleting it on GitHub clears only the third. --prune clears the second, and git branch -D the first.

Watch out

git branch -d will refuse with "not fully merged", and that is expected, not a problem. Squash merging replays your work as one brand-new commit with a different SHA, so your original commits genuinely are not in main. Every squash-merged branch needs -D. Turn on Automatically delete head branches in repo settings to remove one of the three steps.

Part B

Scaffold a new project

Day one. Get a building app and a remote before worrying about pipelines.

06

Create the client in a subfolder

repo root — leave room for server/ beside it

Do 
npm create vite@latest client -- --template react-ts
cd client && npm i react-router-dom axios antd dayjs
Why

One repo with client/ and server/ as siblings, not two repos. A split costs you two remotes and loses atomic commits when an API shape and the hook consuming it change together. Both Vercel and Render support a subdirectory as the project root, which is what makes the monorepo a non-issue.

Watch out

Decide this before the first commit. Restructuring later means rewriting every path in every config file you are about to write.

07

Set up the @/ path alias

vite.config.ts and tsconfig.app.json

Do 
// vite.config.ts
resolve: { alias: { "@": path.resolve(import.meta.dirname, "src") } }

// tsconfig.app.json → compilerOptions
"paths": { "@/*": ["./src/*"] }
Why

They are two separate systems: TypeScript only type-checks, the bundler only resolves, and neither implies the other. Vite 8's Rolldown does read tsconfig paths natively — but keep resolve.alias anyway, because PostCSS never sees tsconfig, so @import "@/x.css" dies with ENOENT without it. The alias covers what TS never touches: CSS, url(), .js.

Watch out

A green build proves nothing until one real file actually imports @/something. Configure it, then use it, then trust it. And never write a bare src/app/App — with no ./ prefix that is a bare specifier and the resolver looks in node_modules/, exactly as it would for react.

08

First commit and remote

Do 
git remote add origin https://github.com/<you>/<repo>.git
git push -u origin main
Why

Everything downstream — CI, release-please, Vercel — is triggered by pushes to this remote. Nothing can be tested until it exists.

Watch out

Your .gitignore must cover node_modules, dist and .env before this push, not after. Once a secret is in history, removing it means rewriting history.

Part C

Repo hygiene before CI

Five small changes. Each one prevents a specific failure later, and all are cheaper to make now than to retrofit.

09

Make lint, Node and env explicit

client/package.json, client/.nvmrc, client/.env.example

Do
  • "lint": "eslint . --max-warnings 0"
  • "engines": { "node": ">=22" }
  • .nvmrc containing 22
  • .env.example documenting each VITE_* variable
  • Set version to 0.1.0 — it must match the release manifest you write in step 19
Why

ESLint exits 0 even when it prints warnings, so without --max-warnings 0 your CI goes green on a warning-filled PR. .nvmrc gives CI a single source of truth via node-version-file, and engines.node is what Vercel reads to pick its build image — so your laptop, CI and production all agree.

Watch out

Tightening lint is a real behaviour change. The first PR that trips react-hooks/exhaustive-deps will fail CI on what used to be silent. That is the point, but it should not surprise you.

10

Add the SPA rewrite before the first deploy

client/vercel.json

Do 
{
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
}
Why

Visit /recipes/123 directly and the host looks for a file at that path, finds none, and returns 404 — your router never gets to run. This says "serve index.html for anything unmatched." It does not break your assets: Vercel checks the filesystem first and only falls through to rewrites when nothing matches.

Watch out

Without this, every deep link and every page refresh 404s in production while working perfectly in npm run dev. It is the classic "works locally" deployment bug.

Part D

CI and GitHub settings

The order here matters: the workflow must run once before GitHub will let you require it.

11

One CI workflow with a change-detection job

.github/workflows/ci.yml

Do

A changes job that always runs, using dorny/paths-filter, plus build jobs gated on its output:

changes:
  outputs:
    client: ${{ steps.filter.outputs.client }}
client:
  needs: changes
  if: ${{ needs.changes.outputs.client == 'true' }}

Steps: npm ci → npm run lint → npx tsc -b → npm run build. Write the server job now; it stays inert until server/ exists.

Why

You want a docs typo to skip the React build. The obvious fix — a workflow-level paths: filter — is a trap: a skipped workflow reports no status at all, and in step 13 you will require that status. A check that never reports is pending forever, so docs-only PRs become unmergeable.

Detect-then-gate avoids it. The workflow always runs, so a check always appears, and a skipped job is counted as a pass.

Watch out

Use fetch-depth: 0 in the changes job — on push events the filter diffs against the previous commit, which a shallow clone cannot do.

12

Three repo settings

GitHub → Settings

Do
  • General → Pull Requests: allow squash merging only; set the squash message to "Pull request title and description"; tick Automatically delete head branches.
  • Actions → General → Workflow permissions: tick Allow GitHub Actions to create and approve pull requests. Leave the radio on read-only.
Why

Squash-only guarantees the PR title becomes the commit message, which is what the release tool reads. Left on GitHub's default message, the commit body is a noisy bullet list of your branch commits. And each workflow declares the permissions it needs, which is safer than granting every workflow write access.

Watch out

The Actions checkbox is the classic hour-waster: without it, release-please fails with a permissions error that never says what is actually wrong.

13

Protect main — after CI has run once

Settings → Branches (or Rules → Rulesets)

Do
  • Require a pull request before merging.
  • Require status checks: changes, client, and the PR-title job.
  • Require branches to be up to date.
  • Do not require approvals.
Why

Require changes as well as client. If changes fails, the client job reports as skipped — which counts as a pass — and a broken PR sails through. Requiring both closes that hole.

No approvals, because GitHub will not let you approve your own PR. Requiring one locks you out of your own repository.

Watch out

The checks dropdown only lists checks GitHub has seen run recently. Open a PR and let CI finish first, or the list is empty. On a private repo this whole screen may also need a paid plan — if so, make the repo public or skip it; nothing downstream depends on it.

14

Lint the PR title

.github/workflows/pr-title.yml · amannn/action-semantic-pull-request

Do
  • Trigger on [opened, edited, reopened, synchronize].
  • Allowlist the conventional types and your scopes (client, server); requireScope: false.
  • subjectPattern: ^(?![A-Z]).+[^.]$ — lowercase first letter, no trailing period.
Why

Because you squash-merge, the PR title is the only commit message that ever reaches main, and therefore the entire input to your version calculation. A PR titled "shopping list stuff" releases nothing, silently — and main's history cannot be reworded afterwards.

Lighter than husky + commitlint, which checks local commits that squashing throws away anyway.

Watch out

edited is load-bearing: without it you fix a bad title and the check stays red with no way to re-run. And a lowercase-first rule bans MP-02 … subjects — decide once whether ticket ids live in the subject or the branch name, and make your docs agree.

Part E

Hosting on Vercel

The goal is contradictory on purpose: let Vercel watch every branch for preview URLs, while never letting it promote anything to production on its own.

15

Import the repo, root directory client

Do
  • Add New → Project → import the repo.
  • Root Directory → client. Framework preset auto-detects Vite.
  • Leave "include source files outside the Root Directory" off.
Why

Root Directory is the single setting that makes a monorepo a non-issue — Vercel treats client/ as the entire project and never looks at docs/ or server/. When the server arrives it becomes a second Vercel/Render project pointing at the same repo with a different root.

Watch out

On import, Vercel immediately deploys your default branch to production. That is unavoidable and harmless — and it usefully proves the build works from a clean checkout. Step 16 is what stops it happening again.

16

Point the production branch at a branch nobody pushes to

Settings → Git → Production Branch, or Settings → Environments → Production → Branch Tracking

Do 
git push origin main:production   # create it remote-only, no local copy

Then set the production branch to production and save.

Why

Vercel now watches everything and still builds a preview for every PR — the single best reason to use it — but it can never find its production branch, so nothing it builds on its own goes live. Production changes only when your deploy workflow runs vercel --prod against a released tag.

The source:destination push form creates the remote branch without a local one, so you cannot accidentally switch to it and commit.

Watch out

The newer UI validates that the branch exists, so create it first or the save fails. It will then offer to "redeploy from production" and find nothing to redeploy — Vercel deduplicates by commit, and that commit was already built. Skip it. Never delete the production branch later; branch tracking breaks and Vercel may fall back to main.

17

Skip builds when nothing in the root directory changed

Settings → Git → Ignored Build Step → Custom

Do 
git diff --quiet HEAD^ HEAD ./
Why

Exit 0 means "no changes here" and the build is skipped; exit 1 means build. It is the Vercel-side equivalent of the changes job in CI, so a docs-only PR stops costing you a React build on both systems.

Watch out

The exit-code logic reads backwards from what you expect. Zero means skip.

18

Create the Vercel token — scoped to the account

Vercel → Account Settings → Tokens

Do
  • Name it after its consumer: github-actions-deploy.
  • Scope: your account/team — not a single project.
  • Expiry: 1 year. Write the date in your journal.
  • Get the two IDs with npx vercel link, which writes .vercel/repo.json containing orgId and the project id.

Store all three as repository secrets (GitHub → Settings → Secrets and variables → Actions): VERCEL_TOKEN, VERCEL_ORG_ID, VERCEL_PROJECT_ID.

Why

The Vercel CLI resolves your identity via /v2/user before doing anything else. An account-scoped token has a user; a project-scoped one does not.

Watch out

A project-scoped token fails in a deeply misleading way. It can call project APIs perfectly well, but whoami returns "User not found" and vercel pull reports "Could not retrieve Project Settings. To link your Project, remove the .vercel directory" — advice that is irrelevant, because CI has no .vercel directory at all.

Rule worth keeping: test a credential in isolation before testing what it accesses.

read -rs TOKEN            # paste, hidden, stays out of shell history
npx vercel@latest whoami --token="$TOKEN"   # must print your username

Also note vercel link appends to your .gitignore without telling you — including a broad .env* that, by last-match-wins, silently overrides an earlier !.env.example. Check with git check-ignore -v path/.env.example.

Part F

Automated releases

release-please reads your commits and maintains one permanently-open Release PR. Merging that PR is the release. Everything else is automatic.

19

Config and manifest

release-please-config.json + .release-please-manifest.json, repo root

Do 
// .release-please-manifest.json
{ "client": "0.1.0" }

// release-please-config.json
{
  "separate-pull-requests": true,
  "pull-request-title-pattern": "chore: release${component} ${version}",
  "bootstrap-sha": "<current main HEAD>",
  "bump-minor-pre-major": true,
  "packages": {
    "client": {
      "release-type": "node",
      "component": "client",
      "include-component-in-tag": true,
      "changelog-path": "CHANGELOG.md"
    }
  }
}
Why

The manifest, not your git tags, is the version. It is an ordinary tracked file that only release-please writes, and only inside a Release PR. Nearly every confusing release-please behaviour traces back to this file disagreeing with reality.

bootstrap-sha says "history starts here", so non-conventional commits from before setup are never parsed. include-component-in-tag produces client-v0.2.0 rather than a bare v0.2.0, so client and server can version independently.

Watch out

Without bump-minor-pre-major, one feat! jumps you from 0.1.0 straight to 1.0.0 — declaring your API stable by accident, with a tag you cannot take back. With it on: fix → 0.1.1, feat → 0.2.0, feat! → 0.2.0.

The ${component} token carries a leading space by design, so chore(${component}): renders as chore( client):. Keep it out of the parentheses.

Only declare packages whose directory exists. Add server in the same PR that creates server/.

20

Create the release PAT — and understand why it is needed

GitHub → Settings → Developer settings → Fine-grained tokens

Do
  • Name: release-please-<repo>. Expiry 1 year, recorded in your journal.
  • Repository access: only that one repo.
  • Permissions: Contents → read and write, Pull requests → read and write. Nothing else. (Metadata read-only is added automatically.)
  • Store as repository secret RELEASE_PLEASE_TOKEN and reference it as the action's token:.
Why

Anything a workflow does with GITHUB_TOKEN is invisible to other workflows. GitHub blocks it to stop workflows recursing. Two consequences, both silent: a tag created by release-please triggers no deploy, and a Release PR it opens receives no CI checks — so your required checks stay pending forever and branch protection refuses the merge. Nothing could ever ship.

A PAT makes the Release PR an ordinary PR that CI runs on. Fine-grained, not classic: a classic token's narrowest useful scope grants access to every repo you own.

Watch out

Create the secret before merging the PR that adds the workflow — it fires on that very merge.

21

Wire the deploy as a called workflow, not a tag trigger

.github/workflows/release-please.yml + deploy.yml

Do 
# release-please.yml — on: push: branches: [main]
deploy:
  needs: release
  if: ${{ needs.release.outputs.released == 'true' }}
  uses: ./.github/workflows/deploy.yml
  with:  { ref: ${{ needs.release.outputs.tag }} }
  secrets: inherit

# deploy.yml — NO tag trigger
on:
  workflow_call:     { inputs: { ref: { required: true, type: string } } }
  workflow_dispatch: { inputs: { ref: { required: true, type: string } } }

Read the outputs as steps.release.outputs['client--release_created'] — manifest mode prefixes every output with the package path.

Why

That if: is the entire "no deploy on every push to main" rule. The output is true only on the push that merged a Release PR; every ordinary merge leaves the job skipped.

Checking out inputs.ref — the tag, not a branch tip — means production gets exactly the blessed commit. Explicit chaining also survives the PAT being rotated away, which a tag trigger would not.

Watch out

secrets: inherit is required — a called workflow receives no secrets otherwise, and your token arrives empty.

Run every vercel command from the repo root, never from client/. The project's Root Directory is already client, and vercel build applies it relative to the working directory — so running it inside client/ resolves to client/client/ and fails with Cannot resolve entry module index.html. For the same reason you need no separate npm ci: vercel build runs the project's own install command.

Part G

Ship it, and prove it

Do this before writing any real feature code, while the only thing that can be broken is the plumbing.

22

Dry-run the whole chain

Do
  • Open a small, genuine feat(client): PR. Merge it.
  • Watch the Release PR "chore: release client 0.2.0" appear. Nothing has shipped yet.
  • Merge the Release PR → tag, GitHub Release, changelog, then the deploy.
  • Open the production URL and confirm the change is live.

Make the change something that displays the version — then "did the release work" is a number you can read on the page rather than a dashboard you have to interpret.

Why

Two human decisions in the whole chain: merge the feature PR, merge the Release PR. The Release PR keeps rewriting itself as more features land, so the release date is simply the day you press merge on it.

Watch out

A failed deploy does not roll back the release — the tag, the Release and the version bump are already real. Release and deploy are separate events, and only one failed. Fix the pipeline, then redeploy the same tag; no new version is needed.

23

Re-deploy or roll back a tag by hand

Actions → Deploy → Run workflow

Do
  • "Use workflow from" dropdown → main
  • "Tag or SHA to deploy" input → client-v0.2.0
Why

The dropdown picks the recipe — which version of deploy.yml runs. The input picks the ingredients — which code gets built. So a fixed pipeline on main can ship an old, unchanged tag. Nothing from main reaches production.

Watch out

Do not "re-run all jobs" on a failed release run: release-please finds nothing left to release, returns release_created: false, the deploy skips, and the run goes green having deployed nothing. And re-runs replay the workflow file as it was, so a fix on main is not picked up. A fresh dispatch is always the safer move.

Command cheat sheet

# daily loop
git switch main && git pull --prune
git switch -c client/mp-02-route-tree
git commit -m "feat(client): add route tree"
git push -u origin client/mp-02-route-tree

# after a squash merge
git switch main && git pull --prune
git branch -D client/mp-02-route-tree     # -d refuses; that is expected

# inspect
git diff main...HEAD                      # exactly what the PR shows
git log main..HEAD --oneline              # commits on this branch (two dots!)
git log --oneline --graph --decorate
git tag -l 'client-v*' --sort=-v:refname
git describe --tags

# diagnose
git check-ignore -v path/to/.env.example  # which rule is hiding my file
git log -1 --format="%an <%ae>"           # who authored this, really
npx vercel@latest whoami --token="$TOKEN" # is the credential itself alive
The one rule behind most of this page

Nearly every failure in this pipeline is silent — a workflow that never fires, a check that never reports, a job that skips and counts as a pass, a green run that deployed nothing. Build the whole chain before you write any feature code, and prove each link with something you can see. Debugging plumbing is easy when plumbing is the only thing that can be broken.
