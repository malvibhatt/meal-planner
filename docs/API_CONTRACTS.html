1. Conventions#

Authentication#

Two tokens, two jobs. Covered in depth by MP-20 → MP-23.

Access token Refresh token
Lifetime 15 minutes 7 days
Travels in Authorization: Bearer <token> Cookie mp_refresh
Readable by JS Yes — keep it in memory, never localStorage No — HttpOnly
Issued by register, login, refresh register, login, refresh

The refresh cookie is scoped to Path=/auth, so the browser sends it to the auth endpoints and nowhere else:

Set-Cookie: mp_refresh=<jwt>; Max-Age=604800; Path=/auth; Expires=...; HttpOnly; SameSite=Lax

secure is added in production. SameSite=Lax works in development because localhost:5173 and localhost:4000 are the same site — ports are not part of a site. A deployment across two domains would need SameSite=None; Secure.

Every endpoint below requires a bearer token except these six: GET /health, POST /auth/register, POST /auth/login, POST /auth/refresh, POST /auth/logout, and GET /uploads/:filename (the static image itself — posting an upload does need a token).

CORS#

CLIENT_ORIGIN (default http://localhost:5173) is the single allowed origin, with Access-Control-Allow-Credentials: true. A wildcard origin is forbidden with credentials, which is why the origin is explicit.

Your axios instance needs withCredentials: true or the refresh cookie is never sent.

Error shape#

Every error is JSON — including 404s for routes that do not exist, so an error interceptor never has to parse HTML.

{ "message": "Human-readable summary" }

Validation failures add a errors object keyed by field name:

{
  "message": "Validation failed",
  "errors": {
    "name": "Name is required",
    "servings": "Servings must be at least 1",
    "caloriesPerServing": "Calories cannot be negative",
    "ingredients": "Add at least one ingredient"
  }
}

Field keys are dotted for nested paths, with the array index included — a bad quantity on the second ingredient row comes back as:

{ "message": "Validation failed", "errors": { "ingredients.1.quantity": "Quantity must be greater than zero" } }

One message per key — the first problem found for that key wins, because a form shows one message per input. MP-42's AC about highlighting a specific row depends on this format.

Status codes#

Code Meaning Notes for the frontend
200 OK
201 Created register, create recipe, create plan entry, upload
204 No content logout, delete recipe, delete plan entry — no body, do not parse one
401 Not authenticated "I do not know who you are" → try refresh, then redirect to login
403 Authenticated but not allowed "I know, and the answer is no" → show the forbidden page, never retry
404 Not found Also returned for things you are not allowed to see, so ids cannot be probed
409 Conflict Duplicate email; same recipe already in that meal slot
422 Validation failed Carries errors — drop them onto form fields
500 Server bug detail is included outside production only

401 vs 403 is load-bearing. MP-23's interceptor refreshes on 401 and retries once; a 403 means the retry would fail identically. MP-24 and MP-25 depend on the distinction too.

Pagination#

List endpoints that can grow return one envelope:

{
  "items": [ ... ],
  "page": 1,
  "pageSize": 2,
  "total": 8,
  "totalPages": 4,
  "hasMore": true
}

Query params: page (default 1, min 1), pageSize (default 20, max 100 — a larger value is a 422, not a silent clamp).

total is there so MP-53 can render "page 3 of 12"; hasMore is there so an infinite scroll does not have to compute it. GET /ingredients is deliberately not paginated — it is a reference list for a <select>.

Date ranges#

?from= and ?to= are both required where they appear, inclusive of both ends, and capped at 92 days. A backwards or oversized range is a 422 on the to field.

3. Auth#

POST/auth/register#

Request

Field Type Rules
email string Trimmed, lowercased, must be a valid email
password string Min 8 characters
name string Trimmed, 1–80 characters 
{ "email": "cook@example.com", "password": "correct-horse", "name": "Everyday Cook" }

201 — also sets the mp_refresh cookie. New users get roles: ["USER"].

{
  "user": {
    "id": "cmuzxtvbq0001hr8ohxoj6vak",
    "email": "cook@mealplanner.test",
    "name": "Everyday Cook",
    "roles": ["USER"]
  },
  "accessToken": "<jwt>"
}

Errors — 409 if the email is taken (with errors.email set, so it lands on the field), 422 on validation.

Emails are lowercased on the way in, so Me@x.com and me@x.com are the same account.

POST/auth/login#

Request

{ "email": "cook@mealplanner.test", "password": "password123" }

200 — identical body to register, plus the mp_refresh cookie.

Errors — 401 { "message": "Invalid email or password" }

That error is identical whether the email is unknown or the password is wrong, and both paths take the same time. Otherwise the login form becomes a way to discover which emails have accounts. Do not try to tell the user which half was wrong — the server will not tell you.

POST/auth/refresh#

No request body and no Authorization header — the cookie alone is the credential. This is what MP-23's interceptor calls on a 401, and what recovers the session after a hard refresh loses the in-memory access token.

200 — a fresh access token, and the refresh cookie is re-issued so an active session slides forward rather than expiring mid-use.

{ "user": { "id": "...", "email": "...", "name": "...", "roles": ["USER"] }, "accessToken": "<jwt>" }

Errors — 401 with no cookie, an expired or tampered cookie, an access token in the cookie, or a user who has since been deleted.

Known limitation: there is no server-side record of issued refresh tokens, so a stolen one stays valid until it expires. Revocation needs a token store — a later ticket.

POST/auth/logout#

No auth required, deliberately: logging out with an already-expired access token must still clear the cookie, and a 401 here would strand the user half-logged-in.

204 — no body. Clears the cookie:

Set-Cookie: mp_refresh=; Path=/auth; Expires=Thu, 01 Jan 1970 00:00:00 GMT; HttpOnly; SameSite=Lax

GET/auth/me#

Requires a bearer token. Reads the database rather than echoing the token's claims, so a name or role changed ten seconds ago shows up immediately.

200

{ "user": { "id": "...", "email": "...", "name": "Everyday Cook", "roles": ["USER"] } }

Errors — 401 with no token, a malformed token, a missing Bearer prefix, or a refresh token used in its place.

roles is an array. MP-25's permission hook should ask "does this include ADMIN?", not compare a single value.

5. Recipes#

Visibility#

A recipe is visible to you if it is isPublic: true or you created it. Admins see everything — not generosity, but consistency: an admin can delete any recipe, so a 404 on reading one they may delete would be a contradiction.

Visibility is applied as a database filter, so total never counts rows you cannot see.

GET/recipes#

Query — the pagination params, plus:

Param Type Notes
q string Case-insensitive substring match on recipe name
ingredientIds comma-separated ids Recipes containing all of them (AND, not OR)

ingredientIds is AND, so each one you add narrows the list — what a filter UI implies. This is not MP-51's pantry filter, which goes the other way (recipes whose ingredients are a subset of what you have, ranked by how many are missing) and will need its own endpoint.

200 — the pagination envelope. Items are summaries, with child counts instead of child rows:

{
  "items": [
    {
      "id": "seed_recipe_chana_masala",
      "name": "Chana Masala",
      "photoUrl": null,
      "servings": 4,
      "caloriesPerServing": 420,
      "proteinPerServing": 18,
      "carbsPerServing": 62,
      "fatPerServing": 10,
      "isPublic": true,
      "createdById": "cmuzxtvb90000hr8ovxkcdj5v",
      "updatedAt": "2026-10-12T21:33:10.410Z",
      "_count": { "ingredients": 11, "prepItems": 2 }
    }
  ],
  "page": 1, "pageSize": 2, "total": 8, "totalPages": 4, "hasMore": true
}

201 — { "recipe": { ... } }, same shape as GET /recipes/:id.

Errors

Code When
422 Validation; also an unknown ingredientId (errors.ingredients) or a duplicate one

An id sent inside prepItems here is ignored — ids cannot be chosen by the client on create.

Quantities are for the whole recipe. 300g of chickpeas for a recipe yielding 4 servings means 75g per serving, and the shopping list scales accordingly.

PUT/recipes/:id#

Owner or admin only. Full replace of the recipe's fields, with one important exception.

Request — same as POST, except each prep step may carry its existing id:

Field Type Behaviour
prepItems[].id string? Supplied → that row is updated in place. Omitted → a new step is created. Missing from the array → that step is deleted

MP-42: send prepItems[].id back

A TodoItem points at a PrepItem, and the todo's status — including a deliberate CANCELLED — lives on that pointer. If the form rebuilds prepItems from scratch without ids, every step is deleted and recreated, so:

  • every resolved todo is orphaned and a fresh PENDING duplicate appears
  • a user's "no, I'm not soaking those" decision is silently undone

Load the recipe with GET /recipes/:id, keep each prepItems[].id, and send it back. Steps the user actually added in the form are the only ones that should have no id.

ingredients need no ids — a RecipeIngredient's identity is (recipeId, ingredientId) and nothing references one, so they are replaced wholesale.

200 — { "recipe": { ... } }

Writing a recipe also rebuilds the prep todos of every meal-plan entry using it — including other users' plans, since a public recipe can be in anyone's. Statuses are preserved; label and dueAt are recomputed.

Errors

Code When
403 Not the owner and not an admin
404 Unknown recipe id
422 Validation; a prepItems[].id that belongs to a different recipe or does not exist (errors.prepItems); the same id twice

Nothing is written when validation fails.

DELETE/recipes/:id#

Owner or admin only.

204 — no body. Cascades to the recipe's ingredients, prep items and meal-plan entries. Catalogue ingredients are never deleted.

Errors — 403 not owner/admin, 404 unknown id.

Deleting a recipe erases every plan entry that ever used it. Worth a confirmation dialog — MP-44's job.

6. Meal plan#

GET/meal-plan#

Query — from and to, both required.

200 — flat and sorted by date then meal type, not grouped by day. MP-60's grid has to render empty slots anyway, so it builds the week's skeleton itself.

{
  "items": [
    {
      "id": "cmv5sx5o30000mw8oxxae59sp",
      "date": "2026-10-13T00:00:00.000Z",
      "mealType": "LUNCH",
      "servings": 2,
      "recipeId": "seed_recipe_chana_masala",
      "recipe": {
        "id": "seed_recipe_chana_masala",
        "name": "Chana Masala",
        "photoUrl": null,
        "servings": 4,
        "caloriesPerServing": 420,
        "proteinPerServing": 18,
        "carbsPerServing": 62,
        "fatPerServing": 10
      }
    }
  ]
}

date comes back as a midnight-UTC timestamp because the column is a DATE. Slice the first ten characters rather than constructing a local Date, or a negative-offset timezone will show the previous day.

Note the two servings: the entry's (how many you are eating) and the recipe's (how many it yields). The ratio is what scales the shopping list.

POST/meal-plan#

Request

Field Type Rules
date string YYYY-MM-DD
mealType MealType
recipeId string Must be visible to you
servings int 1–50, default 1

201

{ "entry": { "id": "...", "date": "...", "mealType": "LUNCH", "servings": 2, "recipeId": "...", "recipe": { ... } } }

Creating an entry generates the prep todos for the recipe's prep steps, in the same transaction.

Errors

Code When
409 That recipe is already in that slot for that day
422 Validation; an unknown or invisible recipeId (errors.recipeId)

Two different recipes in one slot is allowed — the uniqueness is on (userId, date, mealType, recipeId).

DELETE/meal-plan/:id#

204 — no body. Deletes the entry, removes its PENDING todos, and leaves DONE and CANCELLED ones as history with sourceEntryId: null.

Errors — 404 for an unknown id and for another user's entry.

GET/meal-plan/macros#

Daily totals, computed in SQL with a single GROUP BY ROLLUP.

Query — date (YYYY-MM-DD), required.

200

{
  "date": "2026-10-13",
  "totals": { "calories": 840, "protein": 36, "carbs": 124, "fat": 20, "entries": 1 },
  "byMealType": [
    { "mealType": "LUNCH", "calories": 840, "protein": 36, "carbs": 124, "fat": 20, "entries": 1 }
  ]
}

byMealType contains only meals with entries, so an empty day gives [] and zeroed totals rather than four empty rows. Calories are whole numbers; macros are rounded to one decimal. A recipe with null carbs or fat contributes 0, not null.

7. Todos#

Todos are derived, never hand-written. They are generated from a meal-plan entry's recipe's prep steps, and regenerated whenever the plan or the recipe is written.

The prep-timer rule#

Each meal has a clock time (breakfast 08:00, lunch 13:00, snack 17:00, dinner 20:00 — UTC, see the caveat below). Each prep step has leadTimeHours and a timing mode:

timing dueAt Right for
EXACT mealAt - leadTimeHours Marinating, toasting spices, thawing — a literal offset
SLOT the latest prep slot (09:00 or 21:30) at or before mealAt - leadTimeHours Soaking — the lead time is a minimum, and longer is fine

With an 8-hour minimum and SLOT:

  • Tuesday lunch → Monday 21:30, before bed
  • Tuesday dinner → Tuesday 09:00, that morning

A SLOT step is never scheduled for less than its minimum. See server/test/mealTimes.test.ts.

Timezone caveat. Meal times and prep slots are UTC, because date is a timezone-less calendar day and combining the two needs some zone. A user in IST sees "lunch 13:00" meaning 18:30 local. Fixing it means storing a timezone per user — a real feature, not a display tweak.

Status#

Status Meaning
PENDING Not yet dealt with
DONE Finished — completedAt set
CANCELLED Deliberately dismissed — cancelledAt set

Regeneration never touches status, completedAt or cancelledAt. A ticked or dismissed todo keeps its state through any number of plan or recipe writes. completedAt and cancelledAt are mutually exclusive — each is cleared when the status changes to anything else.

Nothing expires a todo. An overdue soak stays on the list, looking as overdue as it is, until the user resolves it. A task that vanishes because its moment passed is how you end up with unsoaked beans.

GET/todos#

Query

Param Type Notes
from YYYY-MM-DD? Optional here, unlike elsewhere
to YYYY-MM-DD? Inclusive of the whole day, not its midnight
status TodoStatus? Omitted means everything — a history view. ?status=PENDING is "what is outstanding"

200 — ordered by dueAt, then label.

{
  "items": [
    {
      "id": "cmv5sx5o90001mw8o7fs4fvyp",
      "label": "Soak the dried chickpeas — Chana Masala",
      "dueAt": "2026-10-12T21:30:00.000Z",
      "status": "PENDING",
      "completedAt": null,
      "cancelledAt": null,
      "sourceEntryId": "cmv5sx5o30000mw8oxxae59sp",
      "sourcePrepItemId": "seed_prep_chana_soak"
    }
  ]
}

Filtering is on dueAt, not the meal's date. A soak for Tuesday lunch is Monday's job, so asking for Monday finds it and asking for Tuesday does not. That is the whole point of the feature — do not "correct" it by filtering on the plan date.

label already includes the recipe name ("Soak the chickpeas — Chana Masala"), so MP-70 does not need to join anything to render a useful line.

PATCH/todos/:id#

Request — status is the only writable field. Labels and due dates are derived; an edit to them would be overwritten by the next regeneration.

{ "status": "DONE" }

200

{
  "todo": {
    "id": "...",
    "label": "Soak the dried chickpeas — Chana Masala",
    "dueAt": "2026-10-12T21:30:00.000Z",
    "status": "DONE",
    "completedAt": "2026-10-12T17:18:23.014Z",
    "cancelledAt": null
  }
}

Errors — 404 unknown id or another user's todo; 422 missing or invalid status.

Any other field in the body is ignored.

8. Shopping list#

GET/shopping-list#

Everything to buy for the meals planned in a range, aggregated in SQL.

Query — from and to, both required.

200 — ordered by category, then name.

{
  "from": "2026-10-13",
  "to": "2026-10-13",
  "items": [
    {
      "ingredientId": "cmuzxtvcd000ghr8oqmnnt2rr",
      "name": "Coriander",
      "category": "PRODUCE",
      "unit": "GRAM",
      "quantity": 7.5,
      "recipeCount": 1
    },
    {
      "ingredientId": "cmuzxtvc60003hr8o5vx8seig",
      "name": "Garlic clove",
      "category": "PRODUCE",
      "unit": "PIECE",
      "quantity": 2,
      "recipeCount": 1
    }
  ]
}

Deduped by ingredient and unit. 200g of yoghurt and 1 tbsp of yoghurt cannot be added, so they are two lines — the same ingredientId can appear more than once with different unit values. Do not key a list by ingredientId alone.

Quantities are scaled by entryServings / recipeServings and rounded to two decimals: cooking one portion of a four-portion recipe puts a quarter of the chickpeas on the list. recipeCount is how many planned recipes contributed to that line.

9. Uploads#

POST/uploads#

multipart/form-data with a single field named file. Requires auth — an open upload endpoint is free file hosting for whoever finds it.

Limit Value
Max size 5 MB
Files per request 1
Other form fields 0
Accepted types image/jpeg, image/png, image/webp, image/avif

201

{
  "url": "http://localhost:4000/uploads/f9239614-30ef-4a65-b11f-c24585990f61.png",
  "filename": "f9239614-30ef-4a65-b11f-c24585990f61.png",
  "size": 70
}

Put url straight into a recipe's photoUrl. It is absolute because an <img src> resolves against the page's origin (the Vite dev server), not the API's. The host comes from PUBLIC_URL.

Errors — all 422 with errors.file:

Message When
Upload a JPEG, PNG, WebP or AVIF image Rejected mime type
File must be 5MB or smaller Over the size limit
No file was uploaded No file field
Upload a single image in the "file" field Wrong field name, too many files

The filename you send is discarded. originalname is attacker-controlled, so the server stores a random UUID plus an extension derived from the validated mime type. Do not expect your name back.

GET/uploads/:filename#

Serves an uploaded image. No directory listing, no dotfiles, cached for 7 days — filenames are random and their content never changes.
